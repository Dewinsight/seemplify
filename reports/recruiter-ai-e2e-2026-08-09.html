Published fixes

The release addressed correctness and tenant safety before model-specific optimization. All listed changes are merged into main.

Runtime

Connected-account workspace resolution

The default ChatGPT subject adapter now forwards the exact organization context. Unauthorized organizations still fail closed.

Assistant

Authoritative WebSocket identity, context, and bounded waiting

Every chat validates the access token, resolves the real actor and active organization, ignores client-supplied identity, enters canonical AI request context, settles terminal errors, and releases the UI after a two-minute downstream timeout.

Jobs

Tenant-safe job and question generation

Interview CRUD/generation/analytics are organization-scoped; exact requested counts and zero-result failures are enforced; job IDs reach credit attribution; department IDs are resolved to human names.

Matching

Scoped cache, invalidation, ranking, and enrichment

Top-K cache retrieval, provider/model/prompt identity, report/bulk rows, tenant checks, vector ranking, candidate invalidation, and authoritative server-side enrichment inputs are corrected.

CV queue

Durable visibility, recovery, and release readiness

Recruiter/admin history, seven-stage timelines, artifacts, errors, attempts, retry/replacement, candidate badges, persistent intake, orphan cleanup, and worker readiness are live and health-gated.

Security

Fail-closed organization boundaries

Jobs, interview questions, matching reports, assistant operations, cache operations, enrichment, bulk upload, public capabilities, and external audit events now preserve tenant isolation.

Provider-neutral AI harness

The optimization is not ChatGPT-only. ChatGPT, Local, and future registered runtimes use the same canonical activity contract; provider, model, and effort remain policy choices.

01 · ContextCanonical inputActor, organization, activity, source application, data class, request ID.
02 · PolicyRuntime choiceAdmin default plus user activity preference selects Local, ChatGPT, or another provider.
03 · HarnessLean prompt + schemaInstructions are stated once; counts, enums, lengths, and required fields live in schema.
04 · ValidationBounded repairStrict output checks, stable idempotency, limited repair context, fail-closed inconsistency.
05 · EvidenceUsage + cache identityProvider, model, effort, prompt version, input fingerprint, tenant, and result state are recorded.
Performance conclusion The largest latency source was repeated sequential model calls and duplicated format instructions, not merely the old Llama model. Deterministic normalization, concurrent independent work, native structured output, smaller repair payloads, and cache correctness are the durable optimizations.

Method and boundaries

The audit separates direct production observation, automated proof, and blocked acceptance so the report does not overstate certainty.

Live production

Signed-in Edge and Codex browser sessions, semantic controls, direct screenshots, a fresh synthetic CV upload, existing active job, processing history, and read-only matching/shortlist inspection.

Parallel workstreams

CV/queue, jobs/questions/Assistant, and matching/cache/enrichment were independently owned, tested, and then reconciled in one release branch.

Safe test-data policy

No real applicant was contacted, no interview invitation was created, no account was disconnected, and no high-cost large-candidate rerank was forced while quota was constrained.

Acceptance boundary

A feature is marked passed only where production evidence or focused automated proof exists. Provider-quota-blocked steps remain explicitly blocked.
